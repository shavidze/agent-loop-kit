# გზამკვლევი: Agent Loop-ის გამოყენება შენს პროექტებში

[English](GUIDE.en.md) · **ქართული**

პრაქტიკული გზამკვლევი: როდის ღირს loop-ის გამოყენება, როგორ მოამზადო პროექტი, როგორ ჩამოაყალიბო მოთხოვნები, როგორ აკონტროლო პროცესი და რა გააკეთო, თუ რამე გაჩერდა.

## 1. როდის ღირს გამოყენება და როდის არა

**ღირს**, როცა:
- სამუშაო დიდია და შეიძლება ბევრ პატარა, შემოწმებად ნაწილად დაყოფა (ფუნქციების სერია, მიგრაცია, bug-ების გრძელი სია);
- პროექტს აქვს ავტომატური შემოწმებები: ტესტები, type check, build (`verifyCommand`);
- შედეგის რეალურად შემოწმება შესაძლებელია: ბრაუზერში, API-ის მეშვეობით ან ფაილებზე.

**არ ღირს**, როცა:
- ამოცანას დაახლოებით ერთი საათი სჭირდება: ასეთ შემთხვევაში პირდაპირ Claude Code-ში გააკეთე;
- პროექტს საერთოდ არ აქვს ტესტები ან build: C-ს არაფერი ექნება შესამოწმებელი. ჯერ მინიმალური ტესტები დაამატე;
- ცვლილებები ეხება საიდუმლო მონაცემებს, ფულს ან production მონაცემებს და ადამიანის review-ის გარეშე არ უნდა გამოქვეყნდეს. ასეთი ფაილები დაამატე `protectedPaths`-ში.

**ხარჯი:** რეალურ პროექტში ერთი რაუნდი დაახლოებით $20–35 ჯდება (A + C + B + reviewer). `metrics/summary.md` ყოველთვის აჩვენებს რეალურ ხარჯს.

## 2. პროექტის მომზადება (ერთჯერადად)

1. **`CLAUDE.md` რეპოზიტორიაში.** აგენტები ყველაზე მეტად ამ ფაილს ეყრდნობიან: ტექნოლოგიური სტეკი, ბრძანებები (dev, test, build), კოდის წესები და აკრძალვები. რაც უფრო ზუსტია ეს ფაილი, მით უკეთ მუშაობს loop. დაამატე `CLAUDE.snippet.md`-ის ტექსტიც.
2. **ერთი verify ბრძანება**, რომელიც ყველაფერს ამოწმებს და წარუმატებლობისას არანულოვან exit code-ს აბრუნებს:
   - Node/React/Remix: `npm run verify` (lint + typecheck + test + build);
   - .NET: `dotnet build -warnaserror && dotnet test`;
   - Flutter: `flutter analyze && flutter test`.
3. **`.claude/agents/code-reviewer.md`**, თუ ჯერ არ გაქვს: A მას იძახებს, როცა ცვლილება 3 ან მეტ ფაილს ეხება. Root gate-ს საკუთარი reviewer (`loop-reviewer`) ჰყავს.
4. **სატესტო სერვერები**, თუ C-ს ბრაუზერი ან API სჭირდება: თითოეული სერვერისთვის `servers`-ში მიუთითე `healthUrl` და გაშვების ბრძანება. თუ სერვერი გათიშულია, loop თავად გაუშვებს.

## 3. კონფიგურაცია

ველების სრული ცხრილი [README-შია](../README.ka.md#კონფიგურაცია-loopconfigjson). რამდენიმე მნიშვნელოვანი შენიშვნა:

- `loopDir` შეინახე რეპოზიტორიის გარეთ, რომ რეპორტები შემთხვევით git-ში არ მოხვდეს.
- `consultAgents`: B და C კოდს არასდროს ცვლიან, ამიტომ მათ მხოლოდ **read-only** პროექტის აგენტები მიეცი (მათ კონფიგურაციაში `Write`/`Edit` არ უნდა იყოს), მაგალითად `accessibility-auditor`, `code-reviewer`, `tech-lead`, `product-manager`. თუ მათი ფაზის დროს source code მაინც შეიცვალა, gate ამ რაუნდის გამოქვეყნებას დაბლოკავს და შექმნის `gates/readonly-violation-*.txt` ფაილს.

## 4. `requirements.md`: ყველაზე მნიშვნელოვანი ფაილი

B სწორედ ამ ფაილის საფუძველზე ქმნის backlog-ს. ბუნდოვანი მოთხოვნები ბუნდოვან შედეგს იძლევა. კარგი მოთხოვნა:
- **ერთი ხაზი = ერთი შემოწმებადი შედეგი**: არა „გააუმჯობესე UX“, არამედ „შეხსენების შექმნა 3 დაწკაპუნებით; ცარიელი სათაურით შენახვისას ველთან შეცდომა ჩანს“;
- **პრიორიტეტით** და **დამოკიდებულებით** („F-04 F-02-ის შემდეგ“);
- მკაფიოდ წერია, **რისი გაკეთება არ გინდა** („auth-ს არ ვცვლით“, „მხოლოდ Android“);
- სადაც შესაძლებელია, მითითებულია **reference** (სხვა პროდუქტის ქცევა, ვიდეოს კონკრეტული დრო); C შედეგს სწორედ მას ადარებს.

მაგალითი:
```markdown
# reminder-app — მოთხოვნები
## უნდა
- F-01 (P1) შეხსენების შექმნა: სათაური + დრო; ცარიელი სათაური → შეცდომა ველთან.
- F-02 (P1) სია დღეების მიხედვით; დღევანდელი ზემოთ.
- F-03 (P2, F-01-ის შემდეგ) განმეორება: ყოველდღე / კვირაში ერთხელ.
## ჯერ არა
- ღრუბელთან სინქრონიზაცია (შემდეგ ეტაპზე).
```

## 5. გაშვება და კონტროლი

- **გაშვება:** `start-loop.cmd` (ან `start-loop.ps1 -Config C:\...\reminder.config.json`). პირველ რაუნდამდე B ქმნის `backlog.json`-სა და პირველ `current-task.md` ფაილს. **ორივე წაიკითხე:** თუ B-მ რამე არასწორად გაიგო, მაშინვე შეასწორე `requirements.md` ან დაამატე წესი `policy.local.md`-ში.
- **დღეში ორი წუთი კონტროლისთვის:**
  - `status.json`: რომელ ეტაპზეა პროცესი;
  - `metrics/summary.md`: ხარჯი, PASS/FAIL, bug-ები;
  - `gates/`: რა გამოქვეყნდა, რა ვერ გამოქვეყნდა და რა მიზეზით;
  - `b-next.json`: B-ს გადაწყვეტილება (CONTINUE / BLOCKED / COMPLETE).
- **მიმართულების შეცვლა:** სანამ loop მუშაობს, კოდი ხელით არ შეცვალო, რადგან A-ს ცვლილებებს შეიძლება შეეჯახოს. ახალი წესი დაამატე `policy.local.md`-ში ან შეცვალე `requirements.md`; B ამას შემდეგ რაუნდში გაითვალისწინებს.
- **გაჩერება:** `stop-loop.cmd`. **გაგრძელება:** `start-loop.cmd -StartRound N -StartPhase A|C|G|B`. პროცესი საკუთარი ფაილებიდან აგრძელებს და არაფერი იკარგება.

## 7. პრაქტიკაში მიღებული გამოცდილება

- **ზედმეტად დიდი ამოცანა ძვირი და არაეფექტური რაუნდია.** თუ ერთი რაუნდი $40-ზე მეტი ჯდება ან C ხშირად FAIL-ს აბრუნებს, `policy.local.md`-ში დაამატე: „ერთი რაუნდი = ერთი ფუნქციის ერთი ეტაპი“.
- **„Offline PASS“ რეალურ PASS-ს არ ნიშნავს.** თუ მეტრიკებში წერია `real: NO`, სერვერები ან ბრაუზერი გამართულად არ მუშაობდა. ასეთ შემთხვევაში გარემო გამოასწორე და არა loop.
- **ისტორია იზრდება.** ამას `context/` ფაილები მართავს, მაგრამ თუ `backlog.json` დაახლოებით 500 KB-ს გადააჭარბებს, B-ს სთხოვე ძველი, დახურული ჩანაწერების არქივში გადატანა.
- **ერთი loop თითო რეპოზიტორიაზე.** ორი პარალელური loop git-ის ისტორიას ერთმანეთში აურევს.
- **ხელით გაკეთებული commit, სანამ loop მუშაობს,** gate-ს HEAD-ს უცვლის. ჯერ გააჩერე loop, გააკეთე commit და შემდეგ გაუშვი `start-loop -StartPhase B`.
- **Windows-ის სპეციფიკური პრობლემები გათვალისწინებულია:** UTF-8 stdin, PowerShell 5.1-ის stderr-ის ქცევა, `pwsh` vs `powershell`, მხოლოდ CR/LF-ით განსხვავებული ცვლილებები.

## 8. პროექტის ტიპების მიხედვით

| პროექტი | verifyCommand | servers | რას ამოწმებს C |
|---|---|---|---|
| Web (React/Remix/Next) | `npm run verify` | dev server (+ API) | ბრაუზერს Playwright-ით, სხვადასხვა viewport-ს |
| .NET API | `dotnet build -warnaserror && dotnet test` | `dotnet run` + health endpoint | რეალურ HTTP მოთხოვნებს, status code-ებს, DB-ის მდგომარეობას |
| Flutter / mobile | `flutter analyze && flutter test` | არ სჭირდება, ან emulator | widget/golden ტესტებს, screenshot-ებს |
| Library / CLI | `npm test` / `pytest` | არ სჭირდება | რეალურ გამოძახებებს, შედეგების შედარებას |
