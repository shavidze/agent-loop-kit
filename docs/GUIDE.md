# გზამკვლევი: Agent Loop-ის გამოყენება პროექტებში

ეს გზამკვლევი პრაქტიკულია: როდის ღირს ლუპის გამოყენება, როგორ მოამზადო პროექტი, როგორ დაწერო მოთხოვნები, როგორ აკონტროლო მუშაობა და რა გააკეთო, როცა რამე ჩერდება.

## 1. როდის ღირს და როდის არა

**ღირს**, როცა:
- სამუშაო დიდია და იყოფა ბევრ პატარა, შემოწმებად ნაწილად (ფუნქციების სერია, მიგრაცია, ბაგების დიდი სია);
- პროექტს აქვს ავტომატური შემოწმება: ტესტები, type check, build (`verifyCommand`);
- შედეგის შემოწმება შეიძლება რეალურად: ბრაუზერში, API-ზე, ფაილებზე.

**არ ღირს**, როცა:
- ამოცანა ერთი საათის საქმეა: უბრალოდ Claude Code-ში გააკეთე;
- ტესტები და build საერთოდ არ არის: C-ს არაფერი ექნება გასაზომი. ჯერ მინიმალური ტესტები დაამატე;
- საქმე საიდუმლოებას, ფულს ან production მონაცემებს ეხება და ადამიანის განხილვის გარეშე არ უნდა წავიდეს. ასეთი ფაილები `protectedPaths`-ში ჩაწერე.

**ფასი:** ერთი რაუნდი რეალურ პროექტზე დაახლოებით $20–35-ია (A + C + B + reviewer). `metrics/summary.md` ყოველთვის აჩვენებს, რა დაჯდა.

## 2. პროექტის მომზადება (ერთხელ)

1. **`CLAUDE.md` რეპოში.** აგენტები ამას ყველაზე მეტად კითხულობენ: stack, ბრძანებები (dev, test, build), კოდის წესები, რა არ შეიძლება. რაც უფრო ზუსტია, მით უფრო ზუსტია ლუპი. დაამატე `CLAUDE.snippet.md`-ის ტექსტიც.
2. **ერთი verify ბრძანება**, რომელიც ყველაფერს ამოწმებს და შეცდომაზე არანულოვან კოდს აბრუნებს. მაგალითები:
   - Node/React/Remix: `npm run verify` (lint + typecheck + test + build);
   - .NET: `dotnet build -warnaserror && dotnet test`;
   - Flutter: `flutter analyze && flutter test`.
3. **`.claude/agents/code-reviewer.md`** (თუ ჯერ არ გაქვს): A მას 3+ ფაილის ცვლილებაზე იძახებს. root gate-ს თავისი reviewer აქვს (`loop-reviewer`).
4. **სატესტო სერვერები**, თუ C-ს ბრაუზერი ან API სჭირდება: `servers`-ში თითოეულისთვის `healthUrl` და გაშვების ბრძანება. ლუპი თავად ჩართავს, თუ გათიშულია.

## 3. კონფიგურაცია (`loop.config.json`)

| ველი | რას ნიშნავს | მაგალითი |
|---|---|---|
| `projectName` | სახელი commit-ებსა და ანგარიშებში | `"reminder-app"` |
| `repoDir` | git რეპო, სადაც აგენტები მუშაობენ | `"C:/Apps/reminder"` |
| `loopDir` | ლუპის მეხსიერება. **რეპოს გარეთ** | `"C:/Apps/reminder-loop"` |
| `branch`, `pushRemotes` | სად წავიდეს შემოწმებული კოდი | `"main"`, `["origin"]` |
| `verifyCommand` | ყველაფრის შემმოწმებელი ბრძანება | `"flutter analyze && flutter test"` |
| `servers` | რა უნდა მუშაობდეს C-სთვის | `[]` თუ არაფერი |
| `protectedPaths` | ფაილები, რომლებიც ლუპის commit-ში არასდროს მოხვდება | auth, payments, secrets |
| `consultAgents` | `.claude/agents`-იდან რომელ აგენტებს გამოიძახებს თითოეული როლი | ქვემოთ |
| `models` | მოდელი როლის მიხედვით (ცარიელი = default) | `"implementer": "claude-opus-5-5"` |
| `commitType`, `commitScope` | commit-ის ფორმატი | `"feat"`, `"studio"` → `feat(studio): ...` |

**`consultAgents`:** B და C კოდს არ ცვლიან, ამიტომ მათ მხოლოდ **read-only** აგენტები მიეცი, ანუ ისეთები, რომლებსაც `Write`/`Edit` არ აქვთ: `accessibility-auditor`, `code-reviewer`, `tech-lead`, `product-manager`. თუ C-ს ან B-ს მუშაობისას source მაინც შეიცვალა, gate იმ რაუნდს არ აქვეყნებს და `gates/readonly-violation-*.txt`-ს წერს.

## 4. `requirements.md`: ყველაზე მნიშვნელოვანი ფაილი

B აქედან აწყობს backlog-ს. ცუდი მოთხოვნა ცუდ ლუპს ნიშნავს. კარგი მოთხოვნა:
- **ერთი ხაზი = ერთი შედეგი**, რომელიც შემოწმებადია: არა „გააუმჯობესე UX“, არამედ „reminder-ის შექმნა 3 დაწკაპუნებაში, ცარიელი სათაურით შენახვა დაბლოკილია“;
- **პრიორიტეტი** და **დამოკიდებულება** („F-04 F-02-ის შემდეგ“);
- **რაც არ გინდა**, ცალკე ჩაწერე: „არ ვცვლით auth-ს“, „მხოლოდ Android“;
- **ნიმუში**, თუ არსებობს: სხვა აპლიკაციის ქცევა ბმულით ან ვიდეოს დროით. C ამას შეადარებს.

მაგალითი:
```markdown
# reminder-app — მოთხოვნები
## უნდა
- F-01 (P1) Reminder-ის შექმნა: სათაური + დრო; ცარიელი სათაური → შეცდომა ველთან.
- F-02 (P1) სია დღეების მიხედვით; დღევანდელი ზემოთ.
- F-03 (P2, F-01-ის შემდეგ) განმეორება: ყოველდღე / კვირაში ერთხელ.
## არ ვაკეთებთ
- სინქრონიზაცია ღრუბელთან (შემდეგ ეტაპზე).
```

## 5. გაშვება და ყოველდღიური კონტროლი

- **გაშვება:** `start-loop.cmd` (ან `start-loop.ps1 -Config C:\...\reminder.config.json`). პირველ რაუნდამდე B წერს `backlog.json`-ს და პირველ დავალებას (`current-task.md`). **წაიკითხე ორივე:** თუ B-მ რამე არასწორად გაიგო, ახლა გაასწორე, `requirements.md`-ის შეცვლით ან `policy.local.md`-ში წესის დამატებით.
- **ყოველდღე 2 წუთი:**
  - `status.json`: სად არის;
  - `metrics/summary.md`: ხარჯი, PASS/FAIL, ბაგები;
  - `gates/`: რა დაიფუშა და რა არა, მიზეზით;
  - `b-next.json`: B-ს გადაწყვეტილება (CONTINUE / BLOCKED / COMPLETE).
- **ჩარევა:** ლუპს კოდში ხელით ნუ ასწორებ, სანამ ის მუშაობს, A-ს ფაილებს შეეჯახება. დაწერე წესი `policy.local.md`-ში ან ცვლილება `requirements.md`-ში. B მას შემდეგ რაუნდში აიღებს.
- **გაჩერება:** `stop-loop.cmd`. გაგრძელება: `start-loop.cmd -StartRound N -StartPhase A|C|G|B`. ფაილებიდან აგრძელებს და არაფერს კარგავს.

## 6. სტატუსები და რა ვქნა

| `status.json` / gate | რას ნიშნავს | რა ქნა |
|---|---|---|
| `WAITING_LIMIT` | Claude-ის ლიმიტი ამოიწურა | არაფერი: reset-ის შემდეგ თავად გააგრძელებს |
| `WAITING_RETRY` | ქსელის შეცდომა | არაფერი: 4-ჯერ სცდის |
| `NEEDS_ATTENTION` | სერვერი ვერ ჩაირთო, ან B-ს შენი პასუხი სჭირდება | `servers/*.log` ან `b-round-N.md` |
| gate `skipped` | C ≠ PASS ან critical/high ბაგია | ნორმალურია, B შემდეგ რაუნდში ასწორებს |
| gate `blocked` | protected ფაილი შეიცვალა, reviewer-მა უარი თქვა, ან C/B-მ source შეცვალა | წაიკითხე `gates/round-N/review.md` / violation ფაილი |
| gate `failed` | verify ჩავარდა | `gates/round-N/verify.log` |
| `AWAITING_ROOT_VERIFICATION` | B-ს აზრით ყველაფერი მზადაა | **თავად გადაამოწმე** პროდუქტი, სანამ დასრულებულად ჩათვლი |

## 7. რჩევები გამოცდილებიდან

- **დიდი დავალება = ძვირი და ცუდი რაუნდი.** თუ რაუნდი $40+ ჯდება ან C ხშირად FAIL-ს წერს, `policy.local.md`-ში დაწერე: „რაუნდი = ერთი ფუნქციის ერთი ეტაპი“.
- **„ოფლაინ PASS“ არ არის PASS.** თუ `metrics`-ში `real: NO` ჩანს, სერვერები ან ბრაუზერი არ მუშაობდა. გაასწორე გარემო, არა ლუპი.
- **ისტორია იზრდება.** `context/` ფაილები ამას აგვარებს, მაგრამ თუ `backlog.json` 500KB-ზე მეტია, სთხოვე B-ს, ძველი დახურული ჩანაწერები არქივში გადაიტანოს.
- **ერთ რეპოზე ერთი ლუპი.** ორი ერთდროულად git ისტორიას გაყოფს.
- **ხელით commit-ი ლუპის დროს** gate-ს „HEAD შეიცვალა“ მდგომარეობაში აგდებს. ჯერ `stop-loop`, მერე commit, მერე `start-loop -StartPhase B`.

## 8. სხვადასხვა ტიპის პროექტი

| პროექტი | verifyCommand | servers | C რას ამოწმებს |
|---|---|---|---|
| Web (React/Remix/Next) | `npm run verify` | dev server (+ API) | ბრაუზერი Playwright-ით, viewport-ები |
| .NET API | `dotnet build -warnaserror && dotnet test` | `dotnet run` + health endpoint | რეალური HTTP მოთხოვნები, სტატუს-კოდები, DB მდგომარეობა |
| Flutter / mobile | `flutter analyze && flutter test` | (არ არის) ან emulator | widget/golden ტესტები, screenshot-ები |
| ბიბლიოთეკა / CLI | `npm test` / `pytest` | (არ არის) | რეალური გამოძახება, output-ის შედარება |
