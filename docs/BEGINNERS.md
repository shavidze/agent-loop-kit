## 1. რა არის ეს, ერთი სურათით

წარმოიდგინე პატარა გუნდი, რომელიც ღამითაც მუშაობს:

| ვინ | ცხოვრებაში | აქ | რას აკეთებს |
|---|---|---|---|
| **B** | მენეჯერი | `loop-planner` აგენტი | კითხულობს შენს სურვილების სიას, ყოფს პატარა ამოცანებად და ყოველ ჯერზე ერთს აძლევს A-ს |
| **A** | დეველოპერი | `loop-implementer` აგენტი | წერს კოდს ამ ერთი ამოცანისთვის |
| **C** | ტესტერი | `loop-verifier` აგენტი | ხსნის რეალურ აპლიკაციას და ამოწმებს, მართლა მუშაობს თუ არა. კოდს **არ** ცვლის |
| **root gate** | უფროსი, რომელიც ხელს აწერს | `run-loop.ps1`-ის ნაწილი + `loop-reviewer` | თუ C-მ თქვა „მუშაობს“, უშვებს ტესტებს, აძლევს სხვა აგენტს გადასახედად და მხოლოდ ამის შემდეგ ატვირთავს კოდს GitHub-ზე |

ეს ოთხი რიგრიგობით მუშაობს და წრეზე ტრიალებს. ერთ წრეს **რაუნდი** ჰქვია. რაუნდი რაუნდს მისდევს, სანამ სიაში ყველაფერი არ გაკეთდება ან შენ არ გააჩერებ.

ყველა აგენტი **Claude Code**-ია, უბრალოდ სხვადასხვა როლითა და უფლებებით. kit თავად AI არ არის. ის „დირიჟორია“, რომელიც Claude Code-ს სწორი თანმიმდევრობით, სწორი ინსტრუქციებით და სწორი შეზღუდვებით იძახებს.

## 2. რას მიიღებ და რას არა

**მიიღებ:**
- დიდი სამუშაო (მაგალითად 30 ფუნქცია ან 50 ბაგი) თანდათან და შენი მუდმივი ჩარევის გარეშე კეთდება;
- ყოველი ცვლილება შემოწმებულია, სანამ შენს რეპოზიტორიაში მოხვდება;
- თუ Claude-ის ლიმიტი ამოიწურა ან ინტერნეტი გაითიშა, ლუპი ელოდება და მერე იქიდან აგრძელებს, სადაც გაჩერდა;
- ყოველი რაუნდის ანგარიში: რა გაკეთდა, რა დაჯდა, რა ჩავარდა და რატომ.

**არ მიიღებ:**
- **ჯადოქრობას.** თუ არ დაწერე, რა გინდა, ლუპი ვერ გამოიცნობს. შენი სურვილების სია (`requirements.md`) ყველაზე მნიშვნელოვანი ფაილია.
- **უფასო სამუშაოს.** ყოველი რაუნდი Claude-ის ტოკენებს ხარჯავს. რეალურ პროექტზე ეს დაახლოებით $20–35 იყო რაუნდში. ზუსტ ციფრს `metrics/summary.md` გაჩვენებს.
- **შენი ბოლო შემოწმების ჩანაცვლებას.** როცა B იტყვის „ყველაფერი მზადაა“, პროდუქტი შენი თვალით ნახე.

## 3. სიტყვები, რომლებიც უნდა იცოდე

| სიტყვა | რას ნიშნავს |
|---|---|
| **რეპოზიტორია (repo)** | შენი პროექტის საქაღალდე, რომელსაც git ადევნებს თვალს |
| **commit** | ცვლილებების „შენახვის წერტილი“ git-ის ისტორიაში |
| **push** | commit-ების ატვირთვა GitHub-ზე (ან სხვა სერვერზე) |
| **branch** | ისტორიის ცალკე ხაზი, მაგალითად `main` |
| **remote** | სად იტვირთება კოდი, ჩვეულებრივ `origin` (შენი GitHub რეპო) |
| **Claude Code** | Anthropic-ის პროგრამა, რომელიც terminal-ში მუშაობს და კოდს წერს. ბრძანებაა `claude` |
| **აგენტი** | Claude Code კონკრეტული როლით და ინსტრუქციით (B, A, C, reviewer) |
| **prompt** | ტექსტური ინსტრუქცია აგენტისთვის: „შენ ხარ C, შეამოწმე…“ |
| **PowerShell, `.ps1`** | Windows-ის სკრიპტების ენა და ამ ენაზე დაწერილი ფაილი |
| **`.cmd`** | Windows-ის „ღილაკი“: ორჯერ დააკლიკებ და შესაბამის `.ps1`-ს გაუშვებს |
| **JSON** | ტექსტური ფორმატი პარამეტრებისთვის: `{"სახელი": "მნიშვნელობა"}` |
| **verify ბრძანება** | ერთი ბრძანება, რომელიც შენს პროექტს ამოწმებს (ტესტები, build). თუ რამე ცუდადაა, შეცდომით სრულდება |
| **სერვერი / health URL** | შენი აპლიკაცია გაშვებულ მდგომარეობაში (მაგ. `npm run dev`) და მისამართი, რომლითაც ლუპი ამოწმებს, ცოცხალია თუ არა (მაგ. `http://127.0.0.1:5173/`) |
| **backlog** | ყველა ამოცანის სია სტატუსებით. B აწყობს და ანახლებს |
| **რაუნდი** | ერთი სრული წრე: A → C → gate → B |
| **gate** | „კარიბჭე“: შემოწმება, რომლის გავლის გარეშე კოდი არ აიტვირთება |

## 4. სამი საქაღალდე

ლუპთან სამი სხვადასხვა საქაღალდე გაქვს. ამის გაგება ყველაზე მეტ დაბნეულობას აგარიდებს:

```
C:\Tools\agent-loop-kit\      ← 1. KIT: თავად ინსტრუმენტი. ერთი ასლი ყველა პროექტისთვის.
    run-loop.ps1, start-loop.cmd, ...
    loop.config.json          ← შენი პარამეტრები (შენ ქმნი)

C:\Apps\my-app\               ← 2. შენი პროექტი (repoDir). აქ წერს A კოდს.
    src\, package.json, CLAUDE.md, .claude\ ...

C:\Apps\my-app-loop\          ← 3. ლუპის მეხსიერება (loopDir). აქ წერენ აგენტები ანგარიშებს.
    requirements.md           ← შენი სურვილების სია (შენ წერ)
    backlog.json, current-task.md, status.json, loop.log, gates\, metrics\ ...
```

**რატომ არის მესამე საქაღალდე პროექტის გარეთ?** ანგარიშები, ლოგები და აგენტების ჩანაწერები რომ შემთხვევით შენს კოდთან ერთად GitHub-ზე არ აიტვირთოს.

## 5. ერთი რაუნდი, როგორც ამბავი

ვთქვათ, `requirements.md`-ში დაწერე: „F-01: შეხსენების შექმნა; ცარიელი სათაური → შეცდომა“.

**დასაწყისი (მხოლოდ ერთხელ).** B კითხულობს შენს სიას და პროექტის კოდს. ქმნის `backlog.json`-ს (ყველა ამოცანა) და `current-task.md`-ს: „რაუნდი 1: გააკეთე F-01. დასრულებულად ჩაითვლება, როცა…“.

**რაუნდი 1:**
1. **სერვერების შემოწმება.** ლუპი ამოწმებს შენს `healthUrl`-ს. თუ აპლიკაცია გათიშულია, თავად რთავს.
2. **A** კითხულობს `current-task.md`-ს, წერს კოდს შენს პროექტში, უშვებს ტესტებს და წერს ანგარიშს `a-round-1.md`-ში. commit-ს **არ** აკეთებს (ეს მას აკრძალული აქვს).
3. **სერვერების შემოწმება კიდევ ერთხელ.** ამჯერად მკაცრად: თუ სამი მცდელობის შემდეგაც არ ჩაირთო, ლუპი ჩერდება და `NEEDS_ATTENTION`-ს წერს. C-ს რეალური აპლიკაცია სჭირდება.
4. **C** ხსნის აპლიკაციას (მაგ. ბრაუზერში), ცდილობს შეხსენების შექმნას, ცდილობს ცარიელ სათაურს. წერს `c-round-1.md`-ს და დასკვნას: PASS ან FAIL, ნაპოვნი ბაგებით. თუ C-ს მუშაობისას კოდი შეიცვალა, ლუპი ამას ამჩნევს და ამ რაუნდს ბლოკავს.
5. **root gate:**
   - C-მ PASS არ თქვა? → `skipped`, არაფერი აიტვირთება;
   - PASS-ია → უშვებს შენს `verifyCommand`-ს. ჩავარდა? → `failed`;
   - გავიდა → ცვლილებებს სხვა აგენტს (`loop-reviewer`) აძლევს გადასახედად. თქვა BLOCK? → `blocked`;
   - თქვა `COMMIT: OK` → **commit + push**. სტატუსი `published`.
   შედეგი იწერება `gates/gate-round-1.json`-ში.
6. **B** კითხულობს ყველაფერს, რაც მოხდა, ანახლებს backlog-ს (F-01 → done ან ხელახლა) და წერს შემდეგი რაუნდის `current-task.md`-ს. მისი გადაწყვეტილება `b-next.json`-შია: `CONTINUE` (გაგრძელება), `BLOCKED` (შენი პასუხი სჭირდება) ან `COMPLETE` (ყველაფერი გაკეთდა).
7. **მეტრიკა.** იწერება, რა დაჯდა და რამდენი დრო წაიღო.

და ასე რაუნდი 2, 3…

## 6. kit-ის ყველა ფაილი უბრალო ენით

**ფაილები, რომლებსაც შენ ეხები:**

| ფაილი | რა არის | რას აკეთებ |
|---|---|---|
| `loop.config.json` | შენი პარამეტრები: სად არის პროექტი, სად ატვირთოს, როგორ შეამოწმოს | ერთხელ ქმნი `loop.config.example.json`-იდან |
| `<loopDir>/requirements.md` | შენი სურვილების სია | ერთხელ წერ, შემდეგ საჭიროებისამებრ ავსებ |
| `<loopDir>/policy.local.md` | შენი დამატებითი წესები ლუპისთვის (არასავალდებულო) | ქმნი, როცა ლუპს რამე სხვანაირად აკეთებინებ |
| `start-loop.cmd` | ჩართვის ღილაკი | ორჯერ დააკლიკებ |
| `stop-loop.cmd` | გამორთვის ღილაკი | ორჯერ დააკლიკებ |

**ფაილები, რომლებსაც ჩვეულებრივ არ ეხები:**

| ფაილი | რა არის |
|---|---|
| `run-loop.ps1` | ლუპის ძრავა: რიგრიგობით იძახებს აგენტებს, ამოწმებს სერვერებს, ელოდება ლიმიტს, უშვებს gate-ს და აკეთებს commit/push-ს |
| `start-loop.ps1` / `stop-loop.ps1` | ის, რასაც `.cmd` ღილაკები რეალურად უშვებს: ფონზე ჩართვა და ყველა პროცესის გათიშვა |
| `agents.json` | ოთხი აგენტის აღწერა: ვის რა უფლება აქვს |
| `prompts/A.md`, `B.md`, `C.md`, `B0-initial.md` | თითოეული აგენტის ინსტრუქცია. `B0-initial` პირველ, საწყის ნაბიჯს ეხება |
| `policy.md` | საერთო წესები, რომლებიც ყველა აგენტს ეგზავნება |
| `templates/` | backlog-ისა და ამოცანის ფაილის ფორმა |
| `tools/build-context.mjs` | ყოველი ფაზის წინ აგენტებისთვის მოკლე „ამონაწერს“ ამზადებს, რომ მთელი ისტორიის კითხვა არ მოუწიოთ |

### ნაბიჯი 4. ჩამოტვირთე kit

```powershell
git clone https://github.com/shavidze/agent-loop-kit C:\Tools\agent-loop-kit
```

### ნაბიჯი 5. შექმენი `loop.config.json`

`C:\Tools\agent-loop-kit`-ში დააკოპირე `loop.config.example.json` და დაარქვი `loop.config.json`. გახსენი Notepad-ში ან VS Code-ში და შეცვალე. სრული მაგალითი პროექტისთვის, რომელსაც სერვერი არ სჭირდება:

```json
{
  "projectName": "my-app",
  "repoDir": "C:/Apps/my-app",
  "loopDir": "C:/Apps/my-app-loop",
  "branch": "main",
  "pushRemotes": ["origin"],
  "verifyCommand": "npm test && npm run build",
  "servers": [],
  "protectedPaths": [],
  "models": { "planner": "", "implementer": "", "verifier": "", "reviewer": "" },
  "consultAgents": { "planner": [], "implementer": [], "verifier": [], "reviewer": [] },
  "commitType": "feat",
  "commitScope": "",
  "roundLimit": 3,
  "maxLimitWaitSeconds": 21600,
  "contextRestartTokens": 650000
}
```

ველი-ველ:
- **`repoDir`**: შენი პროექტის გზა. გამოიყენე `/` და არა `\`;
- **`loopDir`**: ახალი, ცარიელი საქაღალდე პროექტის **გარეთ**. თუ არ არსებობს, ლუპი თავად შექმნის;
- **`branch`** და **`pushRemotes`**: სად აიტვირთოს. პირველი ცდისთვის ცალკე branch სჯობს (იხ. [რჩევები](#11-უსაფრთხოდ-დაწყების-რჩევები));
- **`verifyCommand`**: ნაბიჯი 3-ის ბრძანება;
- **`servers`**: ცარიელი (`[]`), თუ C-ს გაშვებული აპლიკაცია არ სჭირდება. ვებ-აპლიკაციისთვის:
  ```json
  "servers": [
    { "name": "web", "healthUrl": "http://127.0.0.1:5173/",
      "startFile": "cmd.exe", "startArgs": ["/c", "npm", "run", "dev"], "cwd": "C:/Apps/my-app" }
  ]
  ```
  ესე იგი: „თუ `http://127.0.0.1:5173/` არ პასუხობს, `C:/Apps/my-app`-ში გაუშვი `npm run dev`“;
- **`protectedPaths`**: ფაილები, რომლებსაც ლუპი არასდროს ატვირთავს, მაგალითად `"src/auth/login.ts"`. თუ A მათ შეცვლის, gate რაუნდს ბლოკავს და შენ წყვეტ;
- **`models`**: ცარიელი ნიშნავს შენს ჩვეულ Claude მოდელს;
- **`consultAgents`**: თუ პროექტს `.claude/agents/`-ში საკუთარი აგენტები აქვს, აქ ჩაწერ, რომელი როლი რომელს გამოიძახებს. დასაწყისისთვის ცარიელი დატოვე;
- **`roundLimit`**: რამდენი რაუნდის შემდეგ გაჩერდეს. **პირველად 3 დაუწერე**, რომ ნახო, როგორ მუშაობს და რა ჯდება.

### ნაბიჯი 6. დაწერე `requirements.md`

შექმენი `C:\Apps\my-app-loop\requirements.md`:

```markdown
# my-app — მოთხოვნები

## უნდა
- F-01 (P1) შეხსენების შექმნა: სათაური + დრო; ცარიელი სათაურით შენახვა → შეცდომა ველთან.
- F-02 (P1) შეხსენებების სია დღეების მიხედვით; დღევანდელი ზემოთ.
- F-03 (P2, F-01-ის შემდეგ) განმეორება: ყოველდღე / კვირაში ერთხელ.
- BUG-01 (P1) გვერდის განახლებისას სია ქრება.

## ჯერ არა
- ღრუბელთან სინქრონიზაცია.
- შესვლის (login) სისტემის შეცვლა.
```

კარგი სიის წესები:
- **თითო ხაზზე ერთი რამ**, ისე დაწერილი, რომ შემოწმება შეიძლებოდეს. „გააუმჯობესე დიზაინი“ ცუდია. „ღილაკი ‘შენახვა’ ფორმის ქვემოთაა და ცარიელ ფორმაზე გათიშულია“ კარგია;
- **ID** (F-01, BUG-01), **პრიორიტეტი** (P1 = მთავარი) და **დამოკიდებულება** („F-01-ის შემდეგ“);
- **„ჯერ არა“** სექცია: რას არ უნდა შეეხოს.

### ნაბიჯი 7 (სასურველი). დაეხმარე აგენტებს შენი პროექტის გაგებაში

- ბრძანებები: როგორ ირთვება, როგორ ეშვება ტესტები;

ბოლოში ჩასვი `CLAUDE.snippet.md`-ის ტექსტი. რაც უფრო კარგად არის აღწერილი პროექტი, მით უკეთ მუშაობს ლუპი.

### ნაბიჯი 9. პირველი 15–30 წუთი: შეამოწმე, სწორად გაიგო თუ არა

გახსენი `C:\Apps\my-app-loop\status.json`:

როცა `phase` შეიცვლება `A_IMPLEMENTING`-ად, B-მ საწყისი ნაბიჯი დაასრულა. ახლა წაიკითხე:

## 8. როგორ წავიკითხო, რას აკეთებს

| მინდა გავიგო… | სად ვნახო (`loopDir`-ში) |
|---|---|
| ახლა რას აკეთებს? | `status.json`: `phase` და `detail` |
| ყველაფერი, რაც მოხდა, დროის მიხედვით | `loop.log` |
| რა უნდა გააკეთოს ამ რაუნდში? | `current-task.md` |
| რა გააკეთა A-მ? | `a-round-N.md` |
| რა იპოვა C-მ? | `c-round-N.md` |
| აიტვირთა თუ არა და რატომ? | `gates/gate-round-N.json` |
| რა თქვა reviewer-მა? | `gates/round-N/review.md` |
| რატომ ჩავარდა ტესტები? | `gates/round-N/verify.log` |
| რომელი ამოცანებია დარჩენილი? | `backlog.json`, `feature-status.md` |
| რა დაჯდა? | `metrics/summary.md`, `metrics/rounds.csv` |

`phase`-ის მნიშვნელობები: `B_BOOTSTRAP` (საწყისი დაგეგმვა), `A_IMPLEMENTING` (A წერს კოდს), `C_VERIFYING` (C ამოწმებს), `B_PLANNING_NEXT` (B გეგმავს შემდეგს), `ENV_CHECK` (სერვერებს რთავს), `WAITING_LIMIT` / `WAITING_RETRY` (ელოდება), `NEEDS_ATTENTION` (შენ გჭირდება), `AWAITING_ROOT_VERIFICATION` (B-ს აზრით ყველაფერი მზადაა), `ROUND_LIMIT_REACHED` (`roundLimit`-ს მიაღწია).

## 9. როგორ ვმართო: შეცვლა, გაჩერება, გაგრძელება

- **მინდა, სხვანაირად აკეთოს.** ლუპის მუშაობისას კოდს ხელით **ნუ** შეცვლი, A-ს ცვლილებებს შეეჯახება. სამაგიეროდ:
  - ახალი ან შეცვლილი მოთხოვნა → `requirements.md`;
  - წესი („რაუნდი პატარა იყოს“, „ტესტები ყოველთვის დაწერე“) → `policy.local.md`.
  B ამას შემდეგ რაუნდში აიღებს.
- **გაჩერება:** ორჯერ დააკლიკე `stop-loop.cmd`.
- **გაგრძელება:** ორჯერ დააკლიკე `start-loop.cmd`. ლუპი ბოლო ჩაწერილი რაუნდიდან აგრძელებს.
- **კონკრეტული ადგილიდან გაგრძელება** (PowerShell-ში, kit-ის საქაღალდეში):
  ```powershell
  .\start-loop.ps1 -StartRound 5 -StartPhase C
  ```
  ფაზები: `A` (კოდის წერა), `C` (შემოწმება), `G` (gate), `B` (დაგეგმვა).
- **მინდა თავად გავაკეთო commit.** ჯერ გააჩერე ლუპი, გააკეთე commit, მერე ჩართე `-StartPhase B`-ით.

## 10. ხშირი პრობლემები

| რას ხედავ | მიზეზი | რა ქნა |
|---|---|---|
| `NEEDS_ATTENTION` + „Write …requirements.md first“ | `loopDir`-ში `requirements.md` არ არის | შექმენი (ნაბიჯი 6) |
| „Loop already running (pid …)“ | ლუპი უკვე ჩართულია | ჯერ `stop-loop.cmd` |
| gate ყოველ რაუნდში `failed` | `verifyCommand` ჩავარდა | `gates/round-N/verify.log`. გაუშვი იგივე ბრძანება ხელით და გაასწორე |
| `NEEDS_ATTENTION` + „Servers not healthy“ | აპლიკაცია ვერ ჩაირთო ან `healthUrl` არასწორია | `servers/*.log`. შეამოწმე პორტი და ჩართე ხელით, რომ ნახო, მუშაობს თუ არა |
| gate `committed_not_pushed` | commit გაკეთდა, push ვერა | შეამოწმე, მუშაობს თუ არა ხელით `git push` (ავტორიზაცია, branch) |
| gate `blocked` + protected | A-მ დაცული ფაილი შეცვალა | თავად გადახედე. საჭიროა? ხელით გააკეთე commit |
| `WAITING_LIMIT` დიდხანს | Claude-ის ლიმიტი ამოიწურა | არაფერი. reset-ის შემდეგ თავად გააგრძელებს (მაქს. `maxLimitWaitSeconds`) |
| `NEEDS_ATTENTION` + B-ს შეკითხვა | B-ს შენი გადაწყვეტილება სჭირდება | წაიკითხე `b-round-N.md`, უპასუხე `requirements.md`-ში ან `policy.local.md`-ში და ჩართე თავიდან |
| რაუნდები ძალიან ძვირია | ამოცანები დიდია | `policy.local.md`: „ერთი რაუნდი = ერთი ფუნქციის ერთი პატარა ეტაპი“ |
| C ხშირად FAIL-ს ამბობს, `real: NO` | C რეალურ აპლიკაციას ვერ ხედავდა | გაასწორე `servers` და `healthUrl` |

## 11. უსაფრთხოდ დაწყების რჩევები

- **პირველად `roundLimit: 3`.** ნახე ხარისხი და ფასი, მერე გაზარდე.
- **პირველად ცალკე branch.** შექმენი `git switch -c loop-try`, `git push -u origin loop-try`, და კონფიგში დაწერე `"branch": "loop-try"`. თუ მოგეწონა, მერე `main`-ში გააერთიანებ.
- **დაცული ფაილები.** ყველაფერი, რაც ფულს, პაროლებს ან მომხმარებლის მონაცემებს ეხება, `protectedPaths`-ში ჩაწერე.
- **ერთი პროექტი = ერთი ლუპი.** ერთ რეპოზე ორი ლუპი ერთდროულად არ გაუშვა.
- **ბოლო სიტყვა შენია.** როცა ლუპი იტყვის „მზადაა“ (`AWAITING_ROOT_VERIFICATION`), აპლიკაცია თავად გახსენი და შეამოწმე.
